# E-Commerce Sales & Customer Analytics

### End-to-End Data Analytics Project | SQL • Power BI • Power Query • DAX

An end-to-end e-commerce analytics project that transforms customer, order, product and transaction data into business-focused insights. The project combines SQL-based business analysis with data preparation, relational modelling, DAX calculations and an interactive Power BI dashboard.

> **Project objective:** Understand revenue performance, order fulfilment, customer value, product and category contribution, acquisition-channel performance, geographic performance and returns — then present the findings in an interactive report that supports business investigation.

## 1. Project Overview

E-commerce businesses need to understand not only how much they sell, but also where revenue comes from, which products and customers contribute most, how orders move through fulfilment, and whether returns require attention.

This project analyses five core business areas:

- **Sales performance:** revenue, order volume, average order value and monthly trends.
- **Customer analysis:** customer counts, high-value customers and repeat purchasing patterns.
- **Product and category analysis:** product rankings, units sold and category-level revenue contribution.
- **Acquisition analysis:** revenue generated by Organic Search, Email Campaign, Paid Ads, Referral and Social Media.
- **Order and return analysis:** order-status distribution, returned orders and filter-aware return-rate analysis.

The final Power BI deliverable contains a main interactive dashboard and a dedicated product tooltip page. The separate Business Insights report page was intentionally removed; business findings and recommendations are documented in the accompanying project documentation and this README.

The project was designed around practical business questions rather than visuals alone.

- What is the average order value?

### Acquisition-channel performance

## 3. Project Workflow

The project follows an end-to-end analytical workflow:

1. **Understand the business questions** — define the sales, customer, product, channel, fulfilment and return questions to investigate.
2. **Prepare the data** — review source tables, identify data-quality issues and create cleaned tables.
3. **Profile with SQL** — inspect all five raw tables, investigate NULLs and blanks, identify duplicates and conflicting records, validate dates and numeric fields, and check referential integrity.
4. **Transform with Power Query** — standardize fields, correct data types and prepare tables for modelling.
5. **Build the data model** — connect customers, orders, order items, products, categories and a dedicated Calendar table.
6. **Develop DAX measures** — calculate revenue, distinct orders, customers, average order value, return rate and period comparisons.
7. **Build the Power BI report** — create KPI cards, analytical visuals, slicers, a reset control and a custom product tooltip.
8. **Validate the results** — reconcile key totals and test filter behaviour.
9. **Translate findings into business actions** — identify performance drivers and areas that warrant further investigation.

## 5. SQL Analysis and Data Profiling

SQL was used to inspect the five raw source tables before the cleaned data was used for reporting. The supplied SQL analysis notes contain a structured profiling workflow covering table structure, missing values, blank strings, duplicates, conflicting records, formatting issues, invalid dates, numeric-value checks and referential integrity.

The raw tables examined were:

- `customers_raw`
- `orders_raw`
- `order_items_raw`
- `products_raw`
- `categories_raw`

### 5.1 Table structure inspection

The analysis began with `DESCRIBE` statements for the source tables to inspect column names and data types. This is important for confirming that IDs, dates, quantities and prices are stored in suitable types before calculations or joins are performed.

```sql
DESCRIBE customers_raw;
DESCRIBE orders_raw;
DESCRIBE order_items_raw;
DESCRIBE products_raw;
DESCRIBE categories_raw;
```

### 5.2 Customer data profiling

The customer checks covered:

| Check | Purpose / SQL approach |
|---|---|
| Total rows and missing values | `COUNT(*)` with conditional aggregation using `SUM(column IS NULL)` |
| Duplicate customer IDs | `GROUP BY customer_id` and `HAVING COUNT(*) > 1` |
| Duplicate-record inspection | Retrieve the affected customer IDs and inspect all columns |
| Exact duplicate rows | Group by all customer attributes and count repeated combinations |
| Text formatting | `TRIM()`, `UPPER()`, `LOWER()`, `LEFT()` and `SUBSTRING()` |
| Registration-date validity | `STR_TO_DATE()` to test whether text can be parsed as a date |
| Registration-date format | `NOT REGEXP` to identify values outside the expected `YYYY-MM-DD` pattern |
| Blank strings | `TRIM(column) = ''` to distinguish blanks from SQL NULLs |
| Affected-record review | Retrieve rows with blank last name, city or acquisition channel |

**Documented customer findings:**

- The raw customer table contained **302 rows**.
- Customer ID `10089` was identified as an exact duplicate customer record.
- Customer ID `10100` had conflicting records with different cities and required investigation.
- Customer name/city formatting issues were identified.
- One invalid registration date was identified: `31/13/2024`.
- Blank last name, city and acquisition-channel values were identified.

### 5.3 Orders data profiling

The order checks covered:

| Check | Purpose / SQL approach |
|---|---|
| Total rows and NULLs | Conditional aggregation across order ID, customer ID, order date, status and shipping method |
| Duplicate order IDs | `GROUP BY order_id` and `HAVING COUNT(*) > 1` |
| Duplicate inspection | Retrieve full records for the affected order IDs |
| Order-date format | `NOT REGEXP` against the expected date pattern |
| Status consistency | Group by status and count orders to reveal unexpected values |
| Customer referential integrity | `LEFT JOIN` to customers and identify unmatched customer IDs |
| Blank order fields | `TRIM()` checks for blank order date, status and shipping method |
| Affected-record review | Retrieve orders with blank status or shipping method |

**Documented order findings:**

- The raw orders table contained **1,002 rows**.
- Order ID `50061` was identified as an exact duplicate.
- Order ID `50076` contained conflicting records.
- Mixed date formats and one invalid date were identified.
- One blank order status and one blank shipping method were identified.
- The misspelled status `deliverd` was identified.
- Four orders referenced customer ID `10067`, which was missing from the customer table.

The initial NULL check found no SQL NULL values in the five inspected order columns. Separate blank-string checks were still necessary because a blank string is not the same as NULL.

### 5.4 Order-item data profiling

The order-item checks covered:

| Check | Purpose / SQL approach |
|---|---|
| Total rows and missing values | Conditional aggregation for order-item ID, order ID, product ID, quantity, unit price and discount |
| Blank values | `TRIM()` checks, including casting numeric-looking fields to text where needed |
| Problem-record inspection | Retrieve rows with missing quantity or blank discount |
| Negative values | Check negative quantity and numeric price values |
| Price/discount formats | `TRIM()`, `REGEXP`, `REPLACE()` and `CAST()` |
| Discount distribution | Group by trimmed discount value and count occurrences |
| Duplicate order-item combinations | Group by order, product, quantity, unit price and discount |
| Order referential integrity | `LEFT JOIN` to orders to identify unmatched order IDs |
| Product referential integrity | `LEFT JOIN` to products to identify unmatched product IDs |

**Documented order-item findings:**

- The raw order-items table contained **1,743 rows**.
- One missing quantity and one blank discount were identified.
- Negative quantity and negative unit-price values were found and required inspection.
- Price values included text formatting such as `1,299.00`; discount values included percentage formatting such as `10%`.
- One exact duplicate row was identified.
- One invalid order reference and one invalid product reference were identified.

Negative quantities and prices were treated as issues to investigate, not automatically deleted, because such values can sometimes represent returns or adjustments.

### 5.5 Product data profiling

The product checks covered:

| Check | Purpose / SQL approach |
|---|---|
| Total rows and NULLs | Conditional aggregation for product ID, name, category ID, selling price and list price |
| Blank product/category fields | `TRIM()` checks |
| Duplicate product IDs | `GROUP BY product_id` and `HAVING COUNT(*) > 1` |
| Invalid prices | Identify zero or negative selling/list prices |
| Selling price vs list price | Identify cases where selling price exceeds list price |
| Product-name formatting | `TRIM()`, `BINARY`, `UPPER()`, `LOWER()`, `LEFT()` and `SUBSTRING()` |
| Category referential integrity | `LEFT JOIN` products to categories to identify unmatched category IDs |

**Documented product findings:**

- The raw products table contained **43 rows**.
- Product ID `1005` was identified as an exact duplicate.
- Product ID `1021` had conflicting selling prices.
- A missing category ID and a missing list price were identified.
- Product ID `1013` had a negative selling price.
- Product ID `1003` had inconsistent product-name formatting.
- All non-NULL category IDs matched existing category records.

A selling price above list price was treated as a condition to investigate rather than automatically classifying it as an error.

### 5.6 Category data profiling

The category checks covered:

- Total row count and NULL counts for category ID and category name.
- Blank category-name detection using `TRIM()`.
- Retrieval of the affected category record.
- Duplicate category-ID detection using `GROUP BY` and `HAVING`.

**Documented category findings:**

- The raw categories table contained **9 rows**.
- Category ID `6` had a blank category name.
- Category ID `1` (Electronics) appeared as an exact duplicate.
- The profiling summary reported no SQL NULL values in the category table.

### 5.7 SQL techniques demonstrated in the supplied analysis

The uploaded SQL notes demonstrate practical use of:

- `DESCRIBE` for schema inspection.
- `COUNT(*)` and conditional aggregation.
- `IS NULL` and blank-string checks with `TRIM()`.
- `GROUP BY`, `HAVING` and `ORDER BY` for duplicate detection.
- `LEFT JOIN` for checking missing customer, order, product and category references.
- `TRIM()`, `UPPER()`, `LOWER()`, `LEFT()` and `SUBSTRING()` for text-quality checks.
- `STR_TO_DATE()` and `REGEXP` for date validation.
- `CAST()` and `REPLACE()` for numeric-format inspection.
- Full-record inspection before deciding how to handle duplicate or conflicting records.

### 5.8 Important SQL data-quality distinction

The analysis deliberately distinguishes between:

- **NULL:** a missing/unknown SQL value.
- **Blank string (`''`):** an empty text value.
- **Whitespace-only text:** a value containing spaces.
- **Duplicate ID:** the same identifier appears in multiple records.
- **Exact duplicate row:** all inspected field values are repeated.
- **Conflicting record:** the same identifier appears with different attribute values.
- **Invalid reference:** a foreign-key value does not match a record in the referenced table.

These distinctions matter because each issue requires a different investigation and treatment. The raw tables were inspected before cleaning decisions were made; conflicting or ambiguous records were not automatically deleted or assigned invented values.

> **Scope note:** The uploaded SQL notes specifically document raw-table profiling and data-quality investigation. They do not contain the full text of separate revenue-ranking, monthly-sales, customer-ranking or window-function query scripts. Those business analyses are represented in the Power BI report and its documented findings; this README does not claim that the supplied profiling notes contain SQL scripts for every dashboard visual.

## 6. Data Cleaning and Quality Decisions

Data preparation was performed before modelling and reporting. The source data contained missing values, blanks, inconsistent text, duplicate records, conflicting records, invalid dates and data-type issues.

The cleaning approach prioritized consistency while avoiding unsupported assumptions about missing or conflicting information.

### Documented customer-table decisions

| Issue | Treatment |
|---|---|
| Initial customer table contained 302 rows | Reviewed duplicate customer IDs before finalizing the cleaned customer table |
| Customer ID `10089` appeared as a duplicate | Duplicate record removed |
| Customer ID `10100` contained conflicting information | Preserved for review instead of arbitrarily selecting one version |
| Customer ID `10056` had an invalid registration date | Invalid date converted to null rather than inventing a replacement |

### Documented order-table decisions

| Issue | Treatment |
|---|---|
| Inconsistent status text, including `deliverd` | Text standardized and `deliverd` corrected to `Delivered` |
| Order `50023` had a blank status | Blank preserved; no unsupported status assigned |
| Order `50053` had a blank shipping method | Missing value preserved |
| Order `50061` contained an exact duplicate record | Exact duplicate removed |
| Order `50076` had conflicting Delivered and Cancelled records | Conflicting records preserved for investigation |
| Date values required consistent interpretation | English (Canada) locale used for date interpretation |
| Order `50016` contained an invalid date | Invalid date converted to null |
| Order `50006` date required checking | Confirmed as 21 July 2025 |

Other preparation work included reviewing nulls and blanks, standardizing text, correcting data types and preparing the cleaned tables for relationships and reporting.

**Data-quality principle:** Exact duplicates and conflicting records are different issues. Exact duplicates can be removed when confirmed, while conflicting records should be investigated rather than silently discarded. Invalid dates should not be guessed.

## 7. Power BI Data Model

The model connects customers, orders, order items, products, categories and Calendar using one-to-many relationships and single-direction filtering.

| One-side table | Many-side table | Relationship key |
|---|---|---|
| `customers_clean` | `orders_clean` | `customer_id` |
| `orders_clean` | `order_items_clean` | `order_id` |
| `products_clean` | `order_items_clean` | `product_id` |
| `categories_clean` | `products_clean` | `category_id` |
| `Calendar` | Orders table | `Calendar[Date]` → `order_date` |

### Modelling decisions

- Used one-to-many relationships for the business keys.
- Kept cross-filter direction single-direction to maintain predictable filter propagation.
- Created an active relationship from `Calendar[Date]` to the order date.
- Marked Calendar as the date table.
- Sorted Month by Month Number.
- Sorted Year-Month chronologically using a sort column.
- Avoided unnecessary bidirectional relationships.

### Calendar table

A dedicated Calendar table was created using the minimum and maximum order dates.

```dax
Calendar =
ADDCOLUMNS(
    CALENDAR(
        MIN(dim_orders[order_date]),
        MAX(dim_orders[order_date])
    ),
    "Year", YEAR([Date]),
    "Month Number", MONTH([Date]),
    "Month", FORMAT([Date], "MMM"),
    "Year-Month", FORMAT([Date], "YYYY-MM")
)
```

The Calendar table provides a consistent date dimension for the date slicer, monthly reporting and rolling six-month comparisons.

## 8. DAX Measures and KPI Logic

The main dashboard uses five headline KPIs. The following measures show the core calculation patterns used in the report.

### Total Revenue

```dax
Total Revenue =
SUMX(
    Order_items_Clean,
    Order_items_Clean[quantity] *
    Order_items_Clean[unit_price]
)
```

`SUMX` evaluates quantity multiplied by unit price for each order-item row and sums the row-level revenue.

### Total Orders

```dax
Total_Orders_Filtered =
DISTINCTCOUNT(order_items_clean[order_id])
```

Distinct order counting prevents orders with multiple product lines from being counted more than once.

### Total Customers

```dax
Total_Customers =
COALESCE(
    DISTINCTCOUNT(dim_Customers[customer_id]),
    0
)
```

This counts unique customer IDs in the current customer-dimension filter context and returns zero instead of blank when no value is available.

### Average Order Value

```dax
Average_Order_Value =
DIVIDE(
    [Total Revenue],
    [Total_Orders_Filtered],
    0
)
```

Average Order Value is total revenue divided by distinct orders. `DIVIDE` safely handles a zero denominator.

### Return-rate logic

The return-rate measure is filter-aware. It identifies distinct returned order IDs from the orders table, transfers those IDs to the order-item table using `TREATAS`, and divides returned distinct orders by total distinct orders.

This approach allows product/category context to affect return-rate analysis without changing the model to bidirectional filtering.

### Six-month comparison logic

- **Current period:** six-month window ending at the maximum date selected in the Calendar slicer.
- **Previous period:** the six months immediately preceding the current six-month window.
- The measures use date-window logic, including `DATESINPERIOD` and `DATESBETWEEN`, and transfer order IDs with `TREATAS` where required.
- **Relative percentage change:** `(Current period value − Previous period value) ÷ Previous period value`.
- A zero or missing previous-period value is handled without showing a misleading percentage.

For Return Rate, an increase is treated as an adverse movement: the indicator uses red for an increase, green for a decrease and grey when there is no comparison. Relative percentage change is not the same as percentage-point change.

- Focusing on selected fulfilment states.

The Channel slicer filters the report by acquisition channel.

- Investigating the selected channel's revenue and order context.

### Clear All Slicers button

The **Clear all slicers** button resets slicer selections and restores the overall report view. The reset interaction was tested to confirm that the report returns to its default filter state.

## 15. Business Recommendations

The dashboard findings suggest several areas for further business investigation:

1. **Build on Electronics performance.** Monitor demand, product availability, product-level revenue and return rates. Review margin and units sold before making inventory or promotional decisions.
2. **Investigate the August revenue peak.** Review product mix, channel contribution, promotions and demand patterns that coincided with August. Do not assume a cause without further analysis.
3. **Strengthen Organic Search performance.** Continue measuring channel revenue and conversion outcomes; identify which landing pages and products contribute most.
4. **Protect high-value customer relationships.** Monitor the purchase patterns and activity of leading customers. Consider retention or loyalty initiatives and analyse repeat purchasing before estimating customer lifetime value.
5. **Monitor order fulfilment.** Track status mix over time and investigate pending, cancelled or unresolved orders. Add delivery-time data if available for deeper fulfilment analysis.
6. **Investigate returns.** Drill into product- and category-level return rates, review unusually high-return items and monitor the six-month trend.
7. **Improve data classification.** Investigate Blank and Unknown values in status, channel and category fields so future reporting can classify records more consistently.

These are evidence-informed recommendations for investigation. The dashboard does not by itself prove the operational causes behind revenue peaks, returns or customer behaviour.
